# AuthCore v1.3.0 Release Plan

## Release Goal

`v1.3.0` completes the transition from refresh tokens acting as implicit sessions to a first-class
session security model. It also completes a secure browser authentication flow and prepares the
current standalone AuthCore application for a production-like deployment.

The target release includes:

```text
v1.2.0
+ refresh token reuse detection
+ first-class sessions
+ session management API
+ Redis-backed distributed rate limiting
+ HttpOnly refresh cookie transport
+ signed session-bound double-submit CSRF protection
+ updated demo frontend
```

AuthCore remains a standalone browser-facing authentication service in this release. A future BFF,
internal service API, and distributed-system architecture are outside the `v1.3.0` scope.

## Release Scope

### Included

- Refresh token reuse detection and documented compromise response.
- PostgreSQL-backed authentication sessions.
- Refresh token ownership by session.
- Session listing and revocation endpoints.
- Redis infrastructure and shared rate limiting storage.
- HttpOnly refresh cookie transport with body fallback for non-browser clients.
- A `sid` claim in refresh JWTs.
- Signed session-bound double-submit CSRF protection.
- Browser client migration from stored refresh tokens to cookie transport.
- Upgrade path from `v1.2.0`.
- Production configuration, deployment checks, documentation, and release notes.

### Excluded

- BFF or API Gateway.
- Internal AuthCore service API.
- Service-to-service authentication.
- Message broker and Notification Service.
- RS256 and JWKS.
- Roles and permissions.
- Distributed tracing.
- New business services.

## Phase 1: Complete Refresh Session Identity

### Add `sid` to refresh JWTs

The refresh token payload must distinguish the user, authentication session, and individual token:

```json
{
  "sub": "user-id",
  "sid": "session-id",
  "jti": "refresh-token-id",
  "iat": 0,
  "exp": 0
}
```

Claim responsibilities:

- `sub` identifies the user.
- `sid` identifies the authentication session and remains stable during rotation.
- `jti` identifies one refresh token and changes during rotation.

Validated refresh credentials must remain consistent across all persisted state:

```text
JWT sub = refreshToken.userId = session.userId
JWT sid = refreshToken.sessionId = session.id
JWT jti = refreshToken.jti
```

The verified JWT does not replace database validation. PostgreSQL remains the source of truth for
refresh token and session state.

### Required tests

- Login issues a refresh JWT with the created session ID as `sid`.
- Rotation preserves `sid` and generates a new `jti`.
- A new login creates a different `sid`.
- A forged or mismatched `sub`, `sid`, or `jti` is rejected.
- A refresh token belonging to a revoked session is rejected.
- Reuse detection continues to work after the payload change.

## Phase 2: Complete Session and Reuse Semantics

### Session lifecycle

Verify the complete lifecycle:

```text
login
-> active session
-> refresh tokens owned by that session
-> rotation within the same session
-> session revocation
-> revocation of all refresh tokens owned by that session
```

Cover these cases:

- Logout of the current session.
- Logout of all user sessions.
- Revocation of a selected session.
- Revocation of all sessions except the current session.
- Repeated revocation.
- Attempted revocation of another user's session.
- Refresh after session revocation.
- Access token behavior after session revocation.

The release documentation must state that access JWT validation remains stateless. Revoking a
session prevents future refreshes immediately, while an already issued access token remains usable
until its expiration unless this behavior is deliberately changed before release.

### Transaction boundaries

Verify atomic behavior for:

- Login: create session and persist refresh token.
- Refresh: revoke old token, create new token, and update `lastRefreshedAt`.
- Logout: revoke session and its refresh tokens.
- Logout-all: revoke all user sessions and refresh tokens.
- Reuse response: revoke the selected compromise scope consistently.

Integration tests must force a failure after the first write in each important transaction and
verify that partial state is not committed.

### Reuse policy

The intended policy for `v1.3.0` is:

> Presenting a previously rotated refresh token is treated as evidence of credential compromise and
> revokes all active sessions and refresh tokens belonging to the user.

Confirm that the implementation follows this policy and document its usability trade-off: a lost
successful refresh response followed by reuse of the old token also triggers global revocation.

### Concurrent refresh

Test simultaneous refresh requests using the same token. Do not assume that every race follows the
same execution order. Tests and implementation review must establish:

- At most one rotation commits successfully.
- No duplicate active child tokens are created.
- No partial database state is committed.
- The result of the losing request is explicitly defined.
- Any reuse response and global revocation behavior is deterministic and documented.

The demo frontend must use a single-flight refresh operation so concurrent failed API requests share
one refresh promise instead of starting independent rotations. Refresh requests must not be retried
automatically after an unknown network outcome.

## Phase 3: Implement CSRF Protection

### Protection model

Implement signed session-bound double-submit CSRF protection for requests authenticated by the
refresh cookie.

The CSRF token must contain a cryptographically random value and an HMAC signature bound to the
verified refresh token `sid`. CSRF signing must use a dedicated secret that is not shared with access
or refresh JWT signing.

The server must validate:

- Presence of the CSRF cookie.
- Presence of the CSRF request header.
- Equality of the cookie and header token values.
- Token structure and encoding.
- HMAC signature using constant-time comparison.
- Binding to the verified refresh session `sid`.

### Protected endpoints

At minimum, protect cookie-authenticated requests to:

- `POST /auth/refresh`;
- `POST /auth/logout`;
- `POST /auth/logout-all`.

Review all other state-changing endpoints before release. Document why each endpoint does or does not
require CSRF protection, including login CSRF considerations.

### Transport rules

- Cookie-authenticated requests require valid CSRF proof.
- Body-only requests remain supported for non-browser API clients without CSRF proof.
- If a refresh cookie is present, the request is treated as cookie-authenticated.
- A request must not bypass CSRF validation by also supplying a refresh token in the body.
- Invalid or missing CSRF proof must be rejected before an authenticated state change occurs.

### CSRF cookie policy

The CSRF cookie must be readable by frontend JavaScript and must have an explicitly documented
`Secure`, `SameSite`, `Path`, and lifetime policy. It must not contain credentials or grant access by
itself.

Define when the CSRF token is:

- issued;
- retained;
- rotated;
- cleared;
- re-established after page reload.

### Required tests

- Valid cookie and header combination succeeds.
- Missing cookie is rejected.
- Missing header is rejected.
- Cookie/header mismatch is rejected.
- Malformed token is rejected.
- Invalid HMAC is rejected.
- Token bound to another session is rejected.
- Cookie plus body cannot downgrade to the body-only flow.
- Body-only API flow remains supported.
- Refresh rotation preserves the expected CSRF lifecycle.
- Logout and logout-all follow the documented CSRF and cookie cleanup policy.

## Phase 4: Complete the Browser Client Flow

Update the demo frontend to use the secured browser transport:

- Keep access tokens in memory rather than `localStorage`.
- Do not store refresh tokens in `localStorage`, session storage, or React state.
- Send browser credentials using `credentials: 'include'`.
- Read the CSRF cookie and send its value through the documented request header.
- Do not send refresh tokens in request bodies from browser flows.
- Restore an authenticated frontend session after page reload through the protected refresh flow.
- Preserve single-flight refresh behavior.
- Clear frontend authentication state after terminal refresh or logout failures.
- Do not automatically retry refresh after an unknown network outcome.

Add frontend tests for token storage, refresh coordination, CSRF header handling, and logout state
transitions. Run the complete browser flow manually against a production-like HTTPS environment.

## Phase 5: Harden Redis-Backed Rate Limiting

### Configuration

Verify and document:

```text
development -> Redis DB 0
test        -> Redis DB 1
production  -> dedicated production Redis service
```

Validate all required connection values. Add password, TLS, connection timeout, and retry settings
only when required by the selected production deployment rather than as unused configuration.

### Failure policy

Determine the actual behavior of the selected throttler storage adapter when Redis:

- is unavailable during application startup;
- disconnects while the application is running;
- reconnects after an interruption.

Choose and document the availability/security policy. Do not silently fall back to independent
in-memory counters. Test the chosen behavior.

### Distributed behavior

Verify:

- Each configured limiter up to and beyond its boundary.
- Counter expiration after TTL.
- Shared counters across at least two AuthCore instances.
- Isolation of named throttlers.
- Isolation and deterministic cleanup of E2E tests.

### Production Redis policy

- Redis is reachable only through the private deployment network.
- Health checks and restart policy are configured.
- Memory limit and `maxmemory` policy are selected deliberately.
- Eviction must not silently weaken rate limiting guarantees.
- Persistence is optional because throttling counters are ephemeral; document the selected policy.

## Phase 6: Validate Cookie, CORS, and HTTP Security Configuration

### Refresh cookie contract

Production policy:

```text
HttpOnly=true
Secure=true
SameSite=Lax
Path=/auth
```

Verify that:

- `Max-Age` matches the refresh JWT lifetime.
- Cookie removal uses the same cookie name, `Path`, and `Domain` as issuance.
- Cookie values are never logged.
- HTTPS is used in the production-like environment.

### CORS

Configure and test an explicit frontend origin allowlist and credentialed browser requests. Wildcard
origins must not be combined with credentials. Verify allowed and rejected origins.

### Proxy behavior

Document the production request path through the reverse proxy. Configure Express proxy trust only
for known proxies and only where required by the deployment topology. Verify the client IP and
protocol behavior used by logging, session metadata, and security policies.

### Additional HTTP hardening

Review and configure:

- Helmet security headers.
- Request body size limits.
- Sensitive response cache policy.
- Error responses that do not expose internal details.
- Redaction of credentials, tokens, cookies, and secrets.

## Phase 7: Validate the v1.2.0 Upgrade Path

The existing session migration invalidates all persisted `v1.2.0` refresh tokens before adding the
required non-null `session_id` column. This policy is intentional: users retain their accounts but
must log in again after upgrading.

Test the real upgrade path:

```text
1. Create a database using the v1.2.0 schema.
2. Create a verified user and an active refresh token through v1.2.0.
3. Back up the database.
4. Apply all v1.3.0 migrations.
5. Start the v1.3.0 application.
6. Verify that the user record remains valid.
7. Verify that the old refresh token cannot be used.
8. Log in again and verify creation of a new session.
9. Exercise refresh, session listing, and logout.
```

Document:

- Forced re-authentication after upgrade.
- Required database backup.
- Migration execution order.
- Rollback limitations.
- Restore-from-backup procedure if application rollback cannot use the migrated schema.

## Definition of Done

`v1.3.0` is ready when all of the following are true:

- New refresh JWTs contain a verified session-bound `sid`.
- Session and refresh token state remain consistent across all lifecycle operations.
- Reuse and concurrent refresh behavior are deterministic and documented.
- Cookie-authenticated state-changing requests are protected against CSRF.
- Browser flows do not expose or persist raw refresh tokens in JavaScript storage.
- Access tokens are not persisted in browser storage.
- Body-only non-browser clients remain supported without creating a CSRF bypass.
- Redis throttling is shared across application instances and has a documented failure policy.
- Cookie, CORS, HTTPS, proxy, and HTTP security configuration are verified.
- The `v1.2.0` upgrade path and forced re-authentication policy are tested and documented.
- Full backend and frontend verification passes.
- A production-like browser smoke test passes.
- README, Swagger, migration notes, and release notes match actual behavior.
- The release commit is tagged and published as `v1.3.0`.
